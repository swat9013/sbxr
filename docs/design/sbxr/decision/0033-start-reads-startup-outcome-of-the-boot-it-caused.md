# 0033. start は、起こした回の VM の起動時の処理の失敗を見分け、後段へ進まずに非 0 で終える

- Status: Accepted
- Date: 2026-11-19

## 決定

- `sbxr start` が停止中の VM を起こしたら、その回の VM の起動時の処理（kit の startup。boot の再生を含む）の結果を読む。失敗していたら、失敗した段を示して非 0 で終える。VM は稼働中のまま残す
  - 失敗した後は、VM の中の確認（decision/0027）・herdr machine を有効に戻す段（decision/0025）・run を始める段（decision/0028）へ進まない
  - 復旧手順として、直してから `sbxr stop <repo>` → `sbxr start <repo>` で起こし直すことを示す
  - 待つ時間の上限までに終わらないときも、失敗と同じに扱う
- 稼働中の VM への start（VM に触れない経路）では、結果を読まない
- 結果の読み取りと待ちは Sbx adapter の内側に置き（decision/0009）、create と同じ読み方（log の最後の回だけを読む）を使う。herdr の kit の有無によらず読む
- 失敗した段は、log の中の失敗の行をそのまま示す。sbxr の語に訳さない
- Runtime は、「VM は起こせたが起動時の処理が失敗した」を、「VM を起こせない（VM は止まったまま）」と区別できる error で返す

## 根拠

- 前提 18 の実測（system.md、sbx v0.53.0）で次が分かった。`sbx exec <VM> -- true` は、起こした回の起動時の処理が終わるまで戻らない。処理が失敗しても exit 0 で戻る。終了 code だけでは失敗を見分けられず、今の start は boot の再生が失敗した VM でも成功で終わりうる（#156）
- #133 で「待たない」と決めた根拠は、前提 18 が未実測であることだけだった。実測で待てると分かったので覆す
- 失敗したまま後段へ進むと、2 つの問題が起きる。後段の確認が通ると、成功と失敗の文面が混ざる。herdr machine を有効に戻すと、壊れた VM へ herdr が繋ぎにいく。そのため、VM の中の確認が成り立たないとき（UC10 の 4a）と同じく、そこで止める
- 稼働中の VM への start では起動時の処理が走らないので、log の最後の回は前の起動のものである。読むと古い失敗を今回の失敗として示す
- 復旧に stop → start を示すのは、稼働中の VM への start が起動時の処理を走らせず、結果も読まないから
- 段を sbxr の語に訳さないのは、log の文面が sbx に合わせた約束（decision/0009）だから。訳すと同じ約束を 2 か所で保守することになる
- create の経路が待つのは herdr の kit を入れたときだけだが、start では常に読む。start では boot の再生を必ず頼む（decision/0009）ので、起動時の処理が常にあるから

## 却下した代替案

- 待たずに、失敗を後段の VM の中の確認（decision/0027）に任せる: 確認は agent と Docker と herdr の pane だけを見るので、boot の再生の失敗（daemon を戻せない等）を見分けられない
- 失敗を警告にとどめ、後段へ進む: 非 0 にならないので、script から start を呼ぶ利用者が失敗に気付けない
- 稼働中の VM への start でも log の最後の回を読む: 前の起動の失敗を今回の失敗として示す
- lifecycle が log を読む: startup log の文面を adapter の内側に置く決定（decision/0009）を破る

## 見直し条件

置かない（失敗の扱いの決定で、実行の記録から測れる量が無い）
