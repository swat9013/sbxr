# 0033. start は、VM を起こした回の起動時の処理の失敗を見分け、後段へ進まずに非 0 で終える

- Status: Accepted
- Date: 2026-11-19

## 決定

- `sbxr start` が停止中の VM を起こしたら、その回の VM の起動時の処理（kit の startup。boot の再生を含む）の結果を読む。失敗していたら、失敗した段を示して非 0 で終える。VM は稼働中のまま残す
  - 失敗した後は、VM の中の確認（decision/0027）・herdr machine を有効に戻す段（decision/0025）・run を始める段（decision/0028）へ進まない
  - 復旧手順として、次の 2 つを並べて示す。VM の中の一時的な状態が原因なら `sbxr stop <repo>` → `sbxr start <repo>` で起こし直す。宣言（boot 等）を直したなら `sbxr recreate <repo>` で作り直す。原因は sbxr に判別できないので、利用者が選ぶ
  - 待つ時間の上限までに終わらないときも、失敗と同じに扱う。示すのは、待った上限と、その回の log の最後の行（止まった段の手がかり）と、VM 内の log の場所で、「VM の中で処理が続いているかもしれない」と添えて非 0 で終える。VM は稼働中のまま残し、後段へ進まない。復旧手順は失敗のときと同じ
- 稼働中の VM への start（VM を起こさない経路）でも、log の最後の回（今動いている VM を起こした回）の結果を読む。失敗か時間切れなら、停止中の VM を起こした回と同じく止める。失敗は「この VM を起こした回の失敗」として示す
- 結果の読み取りと待ちは Sbx adapter の内側に置き（decision/0009）、create と同じ読み方（log の最後の回だけを読む）を使う。herdr の kit の有無によらず読む
- 失敗した段は、log の中の失敗の行をそのまま示す。sbxr の語に訳さない
- Runtime は、「VM は起こせたが起動時の処理が失敗した」を、「VM を起こせない（VM は止まったまま）」と区別できる error で返す

## 根拠

- 前提 18 の実測（system.md、sbx v0.53.0）で次が分かった。`sbx exec <VM> -- true` は、起こした回の起動時の処理が終わるまで戻らない。処理が失敗しても exit 0 で戻る。終了 code だけでは失敗を見分けられず、今の start は boot の再生が失敗した VM でも成功で終わりうる（#156）
- #133 で「待たない」と決めた根拠は、前提 18 が未実測であることだけだった。実測で待てると分かったので覆す
- 失敗したまま後段へ進むと、2 つの問題が起きる。後段の確認が通ると、成功と失敗の文面が混ざる。herdr machine を有効に戻すと、壊れた VM へ herdr が繋ぎにいく。そのため、VM の中の確認が成り立たないとき（UC10 の 4a）と同じく、そこで止める
- 稼働中の VM でも読むのは、読まないと、失敗で止まった後に利用者がもう一度 start を打ったとき、結果を読まずに herdr machine を有効に戻し、壊れた VM へ herdr が繋ぎにいくから。log の最後の回は今動いている VM を起こした回なので、新しい状態の記録が要らず、外部起動で boot が失敗した VM も拾える
- 稼働中の VM での失敗を「この VM を起こした回の失敗」と示すのは、その回が start の打たれる前の起動だから。今回の start の中で起きた失敗と読み違えさせない
- 復旧に 2 つを並べるのは、boot が作成時に固定されて VM の中に書かれ、起動のたびに宣言を読み直さない（ADR 0006）から。宣言を直したときは stop → start では直らず、作り直しが要る（UC2 の 7a と同じ）。一時的な状態が原因なら起こし直しで足り、作り直すと VM 内の commit と変更が失われる
- 時間切れで上限と log の最後の行と場所を示すのは、時間切れでは log に失敗の行が無く、示す段が無いから。最後の行が止まった段の手がかりになる。処理が VM の中で続いている場合があるので、失敗と言い切らない
- 段を sbxr の語に訳さないのは、log の文面が sbx に合わせた約束（decision/0009）だから。訳すと同じ約束を 2 か所で保守することになる
- create の経路が待つのは herdr の kit を入れたときだけだが、start では常に読む。start では boot の再生を必ず頼む（decision/0009）ので、起動時の処理が常にあるから

## 却下した代替案

- 待たずに、失敗を後段の VM の中の確認（decision/0027）に任せる: 確認は agent と Docker と herdr の pane だけを見るので、boot の再生の失敗（daemon を戻せない等）を見分けられない
- 失敗を警告にとどめ、後段へ進む: 非 0 にならないので、script から start を呼ぶ利用者が失敗に気付けない
- 稼働中の VM への start では結果を読まない: 失敗で止まった後にもう一度 start を打つと、結果を読まずに herdr machine を有効に戻し、0 で終わりうる。外部起動で boot が失敗した VM も拾えない
- 失敗の印を状態ディレクトリに残し、稼働中の VM への start で見る: 新しい状態の記録が要る。sbxr を通さない起動の失敗は印に残らない
- 復旧手順に stop → start だけを示す: 宣言の boot を直したときは、VM の中の boot が作成時のままなので同じ失敗を繰り返す
- lifecycle が log を読む: startup log の文面を adapter の内側に置く決定（decision/0009）を破る

## 見直し条件

置かない（失敗の扱いの決定で、実行の記録から測れる量が無い）
