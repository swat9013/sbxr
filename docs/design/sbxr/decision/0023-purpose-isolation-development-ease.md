# 0023. 目的を隔離・VM の中で開発できる・手軽の 3 つに組み直し、作業の保全を外す

- Status: Accepted
- Date: 2026-11-19

## 決定

sbxr が達成したい状態を次の 3 つにする。

1. **隔離**: agent は sandbox VM の外へ出られず、VM から通信できる宛先は、利用者が create の前に確かめたものだけである。
2. **VM の中で開発できる**: VM の中で agent が、Docker を含む開発の道具を使える。
3. **手軽**: 宣言 1 枚で環境を定義し、1 コマンドで立ち上げ、1 コマンドで止められる。

食い違ったときは、隔離 > VM の中で開発できる > 手軽の順に優先する。

- 「外へ出られない」は、実行基盤の VM の境界（VM-level isolation）に依る。sbxr は、その境界を弱める構成を作らない
- 実値の secret を VM に入れないこと（credential injection）と、repo 宣言を untrusted として確認プロンプトで見せることは、隔離の中身として保つ
- 「作業の保全」は目的から外す。destroy が未 push の作業を検査する決定（decision/0003・0021）は取り下げ、destroy は VM 内の commit と変更が失われることを示して承認を求めるだけにする
- 「再現」は独立した目的にせず、手軽の中身にする。VM は作った後に宣言を取り込まず、宣言を変えたら作り直す（immutable infrastructure）。drift はその合図として残す

## 根拠

- 利用者が求めるのは、agent の隔離環境を手軽に用意することである
- プロセス単位の隔離（OS-level sandbox）では、Docker を使えるようにすると Docker 経由で制限を抜けられた。VM 単位の隔離なら、VM の中に専用の Docker を置ける
- 未 push の作業は、利用者が VM の中から origin へ push すれば残せる。道具の側で検査するには、一時起動・origin への fetch・origin の host の egress 許可と secret の配線が要り、要件に無い目的のために仕組みが増える

## 却下した代替案

- 作業の保全を優先順の最後に残す: 要件に無い目的を残すと、destroy の検査と状態機械の guard が設計に残り続ける
- 再現を独立した目的に残す: 手軽と食い違う場面が無く、優先順を決める軸にならない

## 見直し条件

置かない（目的の決定で、実行の記録から測れる量が無い）
