# 0007. egress 自己検証の「届く」「届かない」を proxy の拒否応答で判定する

- Status: Accepted
- Date: 2026-09-27
- 覆す条件: sbx の proxy の拒否応答（状態コード 403 と body の `Blocked by network policy`）が変わったとき。実測は sbx v0.45.1（[system.md の未実測の前提](../system.md#未実測の前提) 6 の実測）

## 決定

[decision/0006](0006-egress-self-check-from-vm.md) の核（create の最後に VM 内から実際の通信で 1 往復ずつ確かめる）は保つ。0006 が前提 6（許可外は curl が失敗として返る）に置いていた判定だけを、次に置き換える。

- **proxy の拒否応答**: 状態コードが 403 で、body に `Blocked by network policy` を含む応答
- **判定**: VM 内で `https://<host>/` へ GET を 1 回送り（redirect は追わない。時間の上限を置く）、結果を次の表で読む

| 結果 | 許可先への probe | 許可外への probe |
|---|---|---|
| proxy の拒否応答 | 届かない（失敗） | 届かない（通る） |
| それ以外の HTTP 応答（状態コードを問わない） | 届く（通る） | 届いた（失敗） |
| HTTP 応答が無い（curl の失敗） | 届かない（失敗） | 確かめられない（失敗） |

- **許可先の選び方**: 実効の許可集合（global rule の期待集合 ∪ sandbox スコープ rule の宛先）を文字列順に並べ、glob を含まず、port が 443 か port の無い最初の宛先を選ぶ
- **許可外の候補**: `example.com`・`example.net`・`example.org`（IANA の予約 domain）の順に見て、許可集合が 443 を通さない最初の 1 つを使う
- **probe 先が無いとき**: 許可先の条件に合う宛先が無いか、許可外の候補がすべて許可集合に一致したら、その側の probe を省き、省いたことを表示する。もう片方は行う

## 根拠

- 許可外の宛先は proxy（`gateway.docker.internal:3128`）が HTTP 403 で拒否し、既定の curl は exit 0 で返る（前提 6 の実測）。curl の成否では「届かない」を判定できない
- TLS は proxy が終端しているので、状態コードだけでは proxy の拒否と宛先自身の 403 を区別できない。body の文言まで見れば区別できる
- 「届く」を状態コードで絞らないのは、宛先自身の 3xx・4xx も proxy を通って宛先に届いた証拠になるから
- 許可外の probe で curl が失敗したとき（名前解決の失敗・timeout）は、proxy が拒否したのか経路が無いのか分からない。確かめたいのは proxy の policy が効いていることなので、通さない
- redirect を追うと、許可先の redirect 先が許可集合の外にあるとき、許可先の probe が proxy の拒否応答で誤って失敗する
- 許可先を文字列順の最初にするのは、宣言が同じなら毎回同じ宛先を叩くため。port の無い宛先は全 port を通すので 443 も通す
- 許可外の候補を IANA の予約 domain にするのは、利用者が許可集合に入れる理由がなく、応答を返し続けるから
- probe 先が無いのは宣言の選択（全 group を除外した VM など）なので、create を止める理由にしない

## 却下した代替案

- `curl -f` の exit code で判定する: 許可先が 4xx を返すと「届かない」に、許可外の候補が 4xx を返すと「拒否された」に誤判定する
- 状態コードだけで判定する: 宛先自身の 403 と proxy の拒否を区別できない
- `--noproxy '*'` で送る: proxy を迂回するので、確かめたい proxy の policy を通らない（実測では許可外が名前解決の失敗になった）
- 許可外の probe で curl が失敗したら「届かない」とみなす: proxy を通らない経路の失敗でも通ってしまう
- probe 先が無いときに create を止める: 許可先を持たない宣言が作れなくなる
